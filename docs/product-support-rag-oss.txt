=====================================================================
1. PROJECT PURPOSE
=====================================================================

Product Support OSS is a local RAG-based AI support assistant for
e-commerce product catalogs.

It answers customer support questions using store data:

    - products;
    - product descriptions;
    - technical specifications;
    - manuals;
    - FAQ;
    - delivery and return policies;
    - warranty rules;
    - category knowledge.

The system is designed for scenarios like:

    - Seller support assistant.
    - Product catalog support chatbot.
    - E-commerce first-line support.
    - Internal assistant for marketplace managers.
    - Product knowledge base search.
    - Support ticket deflection.
    - Future PIM/ERP/e-commerce integration layer.

The main idea:

    User creates a store.
    Store contains products.
    Products contain descriptions and technical specifications.
    Backend transforms product data into knowledge chunks.
    Chunks are embedded and stored in Qdrant.
    User asks a question.
    System retrieves relevant product knowledge from Qdrant.
    Qwen 2.5 generates a grounded answer.
    UI shows answer and sources.
    Dashboard shows token usage, latency, retrieval stats, and errors.

This project demonstrates practical AI Engineering skills:

    - RAG pipeline;
    - product knowledge ingestion;
    - chunking;
    - embeddings;
    - Qdrant vector search;
    - metadata filtering by store/product;
    - prompt construction;
    - local LLM integration;
    - token usage tracking;
    - hallucination guardrails;
    - Rust backend;
    - SQLite persistence;
    - Docker deployment;
    - Nuxt frontend;
    - observability dashboard.

3. TARGET USERS
=====================================================================

Primary users:

    1. E-commerce store owners.
    2. Marketplace support teams.
    3. Developers building AI support assistants.
    4. Product teams needing product catalog chatbots.
    5. Internal knowledge base owners.
    6. Recruiters and technical interviewers reviewing AI Engineering skills.
    7. Indie hackers building AI automation products.

User pain:

    - Support answers the same product questions repeatedly.
    - Product data is scattered across descriptions, specs, FAQ, and docs.
    - Generic LLM chatbots hallucinate.
    - Answers lack sources.
    - Local LLM integration is often messy.
    - Vector search and retrieval quality are hard to debug.
    - Token usage and latency are not visible.
    - RAG quality is hard to evaluate.

Value proposition:

    Create a store, add products, index product knowledge, and get a
    grounded AI assistant that answers product questions with sources,
    token usage, latency, and quality controls.

4. MVP SCOPE
=====================================================================

The MVP must support the following flow:

    1. User creates a store.
    2. User adds products manually or via API.
    3. Backend transforms product data into knowledge chunks.
    4. Chunks are embedded.
    5. Embeddings are upserted into Qdrant.
    6. Metadata is stored in SQLite.
    7. User asks a question through UI or API.
    8. Backend embeds the question.
    9. Backend searches relevant chunks in Qdrant with store filter.
    10. Optional keyword search can be performed via SQLite FTS5.
    11. Backend builds a grounded prompt.
    12. Qwen 2.5 generates an answer.
    13. Backend stores conversation message and usage metrics.
    14. UI displays answer and sources.
    15. Dashboard shows token usage, latency, retrieval stats, errors.

Core features:

    1. Stores CRUD.
    2. Products CRUD.
    3. Product knowledge ingestion.
    4. Chunking of descriptions, specs, FAQ, manuals.
    5. Local embedding generation.
    6. Qdrant collection management.
    7. Qdrant point upsert/delete.
    8. Metadata filtering by store_id/product_id.
    9. SQLite storage for relational data.
    10. Optional SQLite FTS5 keyword retrieval.
    11. Hybrid retrieval: Qdrant vector + FTS keyword.
    12. Top-K retrieval.
    13. Source citations.
    14. Qwen 2.5 chat integration.
    15. Streaming answer support if practical.
    16. Token usage tracking.
    17. Latency tracking.
    18. Request history.
    19. Simple dashboard.
    20. Docker Compose deployment.
    21. Health endpoint.
    22. OpenAPI/Swagger documentation if practical.

Optional but desired MVP enhancements:

    1. Reindex button in UI.
    2. Products list page.
    3. Chunk viewer.
    4. Retrieval debug panel.
    5. Conversation history.
    6. Feedback thumbs up/down.
    7. Evaluation dataset.
    8. Lightweight mode with external OpenAI-compatible provider.
    9. Cache for repeated questions.
    10. CSV product import.

10. CORE USER FLOWS
=====================================================================

Flow 1: Store and product creation

    1. User creates a store via UI or API.
    2. User adds products via UI or API.
    3. Product contains:
        - name;
        - category;
        - description;
        - specs;
        - manual;
        - FAQ;
        - status.
    4. Backend stores product in SQLite.

Flow 2: Knowledge ingestion

    1. Backend receives reindex request or product create/update event.
    2. Backend loads products for selected store.
    3. Backend transforms product fields into knowledge chunks.
    4. Backend computes chunk identifiers and hashes.
    5. Backend generates embeddings for chunks.
    6. Backend upserts points into Qdrant.
    7. Backend stores chunk metadata in SQLite.
    8. Backend stores qdrant_point_id in SQLite chunks table.

Flow 3: User asks a question

    1. User opens Nuxt frontend.
    2. User selects store.
    3. User types a question.
    4. Frontend sends POST /api/v1/chat.
    5. Backend embeds the question.
    6. Backend searches Qdrant with store_id filter.
    7. Optional SQLite FTS5 keyword search is performed.
    8. Backend merges retrieval results.
    9. Backend builds grounded prompt.
    10. Backend calls Qwen 2.5.
    11. Backend streams or returns answer.
    12. Backend stores message and usage metrics.
    13. UI displays answer and sources.

Flow 4: Reindex products

    1. User opens Products page.
    2. User clicks Reindex.
    3. Backend scans selected store products.
    4. Backend deletes outdated Qdrant points.
    5. Backend regenerates chunks and embeddings.
    6. Backend upserts new points.
    7. Backend shows indexing status.

Flow 5: Dashboard inspection

    1. User opens Dashboard page.
    2. Backend returns summary metrics.
    3. UI displays:
        - total stores;
        - total products;
        - total chunks;
        - Qdrant points count;
        - total chats;
        - success rate;
        - total tokens;
        - average latency;
        - cache hits;
        - retrieval statistics;
        - recent errors.

      }
    }

=====================================================================
15. PROMPT DESIGN
=====================================================================

Design principles:

    1. Prompt must be grounded in retrieved product knowledge.
    2. Model must not use outside knowledge when context is enough.
    3. Model must cite source numbers.
    4. Model must say when product data does not contain an answer.
    5. Temperature should be low.
    6. Prompt should be versioned.
    7. Prompt should be safe against prompt injection.
    8. Retrieved chunks are data, not instructions.
    9. Answer should be concise.
    10. Backend should store prompt metadata for debugging.

Example system prompt:

    You are an e-commerce product support assistant.
    Answer only using the provided product knowledge chunks.
    If the provided chunks do not contain enough information, say:
    "The provided product data does not contain an exact answer."
    Do not invent specifications, prices, deadlines, warranty terms,
    delivery rules, or compatibility.
    Use citations like [1], [2] when referring to chunks.
    Be concise and helpful.

Example user prompt:

    Store: {store_name}
    Question: {question}

    Product knowledge chunks:

    [1] Product: Red T-shirt with print
    Field: specs.material
    Content: cotton

    [2] Product: Red T-shirt with print
    Field: description
    Content: Cotton t-shirt with bright print.

    Answer the question using only these chunks.
    Include citations.

16. RETRIEVAL DESIGN WITH QDRANT
=====================================================================

Qdrant role:

    Qdrant is the vector database used for semantic retrieval of
    product knowledge chunks.

Collection:

    product_support_chunks

Vector config:

    {
      "size": VECTOR_DIM,
      "distance": "Cosine"
    }

Payload fields:

    {
      "store_id": "uuid",
      "product_id": "uuid",
      "chunk_id": "uuid",
      "source_type": "product_spec",
      "field_path": "specs.material",
      "product_name": "Red T-shirt with print",
      "section_title": "Specifications",
      "content": "cotton",
      "content_hash": "sha256",
      "embedding_model": "nomic-embed-text",
      "vector_dim": 768,
      "updated_at": "2026-08-27T12:00:00Z"
    }

Recommended payload indexes:

    store_id
    product_id
    source_type
    updated_at

Retrieval flow:

    1. Embed user question.
    2. Search Qdrant collection.
    3. Apply mandatory store_id filter.
    4. Optional product_id filter.
    5. Retrieve top K points.
    6. Load chunk metadata from SQLite if needed.
    7. Optional SQLite FTS5 keyword search.
    8. Merge results using score fusion.
    9. Select final top K chunks.
    10. Build prompt.

Hybrid scoring example:

    final_score =
        0.6 * qdrant_score_normalized
      + 0.4 * fts_score_normalized

Chunking rules:

    - Product name becomes a separate searchable chunk.
    - Description is split into chunks.
    - Each spec key/value can become a chunk.
    - FAQ question/answer pairs become chunks.
    - Manual text is split by headings or length.
    - Store policy text can be attached as store-level chunks.
    - Default chunk size: 600-1000 characters.
    - Default overlap: 80-160 characters.
    - Avoid chunks smaller than 80 characters.
    - Avoid chunks larger than 2000 characters.

Retrieval quality controls:

    - If top score is too low, answer with low-confidence notice.
    - If no chunks found, say product data has no answer.
    - Do not force an answer.
    - Store retrieval debug metadata.
    - Show sources in UI.

---------------------------------------------------------------

);

---------------------------------------------------------------
TABLE messages
---------------------------------------------------------------

CREATE TABLE messages (
    id TEXT PRIMARY KEY,
    conversation_id TEXT NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    role TEXT NOT NULL,
    content TEXT NOT NULL,
    sources TEXT,
    provider TEXT,

TABLE usage_metrics
---------------------------------------------------------------

CREATE TABLE usage_metrics (
    id TEXT PRIMARY KEY,

    completion_tokens INTEGER,
    total_tokens INTEGER,
    token_source TEXT,
    estimated_cost REAL,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE INDEX idx_usage_message_id ON usage_metrics(message_id);

Qdrant storage:

    Qdrant stores only vectors and payload needed for retrieval.
    SQLite stores chunk content and qdrant_point_id.
    If Qdrant point is lost, reindex can rebuild it from SQLite chunks.

Consistency strategy:

    - Chunk creation writes SQLite first.
    - Embedding upsert writes Qdrant point.
    - SQLite chunk stores qdrant_point_id.
    - Product deletion deletes SQLite chunks and Qdrant points.
    - Reindex can delete all points for store/product and rebuild.
    - Health/reconciliation endpoint can compare SQLite chunk count and
      Qdrant points count.

Input validation:

    Limit question length.
    Validate product payload.
    Sanitize store/product identifiers.

    Validate citation format if used.

    Use .env file for local development.
    Provide .env.example.

26. ARCHITECTURE DECISIONS
=====================================================================

Decision 1: Rust backend

    Reason:
        Performance, safety, strong portfolio signal, alignment with
        Korgi.Beats and Korgi.Vision services.

Decision 2: SQLite3 for relational MVP data

    Reason:
        Zero external relational database dependency.
        Easy local demo.
        Enough for single-node OSS demo.
        Simple backup as one file.

    Trade-off:
        Not suitable for high-concurrency production without migration.
        Commercial version should consider PostgreSQL.

Decision 3: Qdrant for vector search

    Reason:
        Dedicated vector DB with filtering, payload indexes, and
        scalable retrieval.
        Better than storing embeddings only in SQLite for RAG demo.
        Shows production-like AI architecture.

    Trade-off:
        Adds another service to Docker Compose.
        Requires consistency handling between SQLite and Qdrant.

Decision 4: Qwen 2.5 as local chat LLM

    Reason:
        Good lightweight local LLM option.
        Can run in Docker.
        Suitable for grounded support answers.

    Trade-off:
        CPU inference may be slow.
        Context length should be limited.
        Model output must be validated.

Decision 5: Separate embedding model

    Reason:
        Qwen chat model is not an embedding model.
        Retrieval requires vector representations.

    Trade-off:
        Need another small model in runtime.
        Embedding quality affects retrieval.
        For Russian docs, embedding model choice matters.

Decision 6: Hybrid retrieval

    Reason:
        Qdrant captures semantic similarity.
        SQLite FTS captures exact keywords.
        Hybrid improves product QA reliability.

Decision 7: Token usage tracking from day one

    Reason:
        AI systems must be observable.
        Commercial product needs cost and usage analytics.
        Portfolio project should demonstrate production thinking.

Decision 8: Provider abstraction

    Reason:
        Qwen runtime may be replaced by:
            Ollama
            llama.cpp server
            OpenAI-compatible API
            custom inference server

        Qdrant may be replaced by:
            pgvector
            Milvus
            Weaviate

        Backend should not depend on one implementation.

=====================================================================
27. RISKS AND MITIGATIONS
=====================================================================

Risk 1:
    Qwen 2.5 hallucinates despite retrieved context.

Mitigation:
    Low temperature.
    Strict system prompt.
    Source citations.
    Low-confidence answer path.
    Evaluation dataset.

Risk 2:
    Retrieval quality is poor for Russian product data.

Mitigation:
    Use hybrid retrieval.
    Choose multilingual embedding model.
    Tune chunk size.
    Store product names and spec keys in chunks.
    Add synonyms/keyword normalization later.

Risk 3:
    Embedding model does not support Russian well.

Mitigation:
    Prefer multilingual embedding model if available.
    Use SQLite FTS keyword retrieval as fallback.
    Document limitation.
    Allow external embedding provider.

Risk 4:
    CPU inference is slow.

Mitigation:
    Use qwen2.5:1.5b-instruct for MVP.
    Limit context.
    Cache repeated questions.
    Show latency metrics.
    Document hardware expectations.

Risk 5:
    SQLite and Qdrant become inconsistent.

Mitigation:
    Store qdrant_point_id in SQLite chunks.
    Provide reindex endpoint.
    Provide reconciliation endpoint.
    Delete product should delete both SQLite chunks and Qdrant points.
    Force reindex can rebuild collection payload for store.

Risk 6:
    Qdrant collection dimension mismatch after changing embedding model.

Mitigation:
    Store VECTOR_DIM in config.
    Health check compares expected dimension and collection config.
    Reindex script can recreate collection.
    Include embedding_model in payload and chunk metadata.

Risk 7:
    Product data contains instructions that could inject prompt.

Mitigation:
    Treat chunks as data.
    Keep system prompt controlled.
    Do not execute instructions from chunks.
    Sanitize rendered output in UI.

Risk 8:
    Token usage unavailable from runtime.

Mitigation:
    Use runtime-reported usage if available.
    Otherwise estimate tokens.
    Store token_source field.

30. README MESSAGE DRAFT
=====================================================================

Suggested short README intro:

    Product Support OSS is a local RAG-based AI support assistant for
    e-commerce product catalogs, built with Rust, Axum, SQLite, Qdrant,
    Docker, Qwen 2.5, and Nuxt 3.

    It indexes stores, products, technical specifications, descriptions,
    FAQ, and manuals, retrieves relevant knowledge from Qdrant, and
    answers customer support questions with citations, token usage,
    latency metrics, and low-confidence guardrails.

    The project is an open-source demo, portfolio seed, and foundation
    for the future commercial product korgi.support.

32. DEFINITION OF SUCCESS
=====================================================================

The project is successful if:

    1. It can be started with a few commands.
    2. It looks like a product, not a script.
    3. It demonstrates RAG engineering discipline.
    4. It demonstrates Qdrant vector search with metadata filtering.
    5. It tracks tokens and latency.
    6. It validates retrieval and LLM output.
    7. It has clear architecture.
    8. It has demo stores/products and evaluation cases.
    9. It can be shown in a resume or interview.
    10. It can be extended into a commercial product.
    11. It integrates naturally with Korgi ecosystem.
    12. It acts as foundation for korgi.support.
